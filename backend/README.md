# Приём заявок: Yandex Cloud Functions + приватный YDB Serverless

Код подготовлен для существующего сайта montazh360.ru. Фронтенд остаётся на GitHub Pages; DNS и текущая публикация не менялись. API и worker не развёрнуты, облачные ресурсы и платные вызовы не создавались. CLI yc и Terraform в окружении не обнаружены. Доступа к параметрам нового облачного размещения, секретам бота и согласованному лимиту расходов для активации нет.

## Что действительно работает и проверено

api.handle выполняет серверную валидацию и возвращает успех только после атомарного сохранения заявки, idempotency-записи и задания уведомления. Повтор с тем же UUID и данными возвращает тот же ID; другой payload с тем же ключом — 409. В YDB используется serializable read/write транзакция и retry SDK. Индивидуальные поля или исключения SDK в HTTP-ответы и журналы не выводятся. Логирование тел запросов в API Gateway/функциях включать не нужно.

Проверены 15 серверных сценариев на синтетике с потокобезопасным in-memory адаптером: валидация, origin, размер, UUID, 40 параллельных повторов, конфликт данных, потеря подтверждения после записи, недоступность хранилища, лимиты, lease и повтор уведомления. Сквозной браузерный тест отправил форму через настоящий локальный HTTP-адаптер, симулировал потерю первого ответа и подтвердил: одна запись, одно outbox-задание, тот же retry key и одно событие только после полученного ID. Ответ 200 без ID отдельно отвергнут. Реальные счётчик, Telegram и облако в этих тестах не вызывались.

**Не проверены живые YDB/Cloud Functions/IAM, применение DDL, доставка настоящим ботом и получение целей панелью Метрики.** SDK pinned на 3.37.0 по официальному PyPI; он будет установлен платформой при сборке функции. На Mac SDK и облачные CLI не устанавливались. До активации обязателен облачный тест синтетикой.

## Устройство

- api.py: HTTP-адаптер API Gateway v1; только POST/OPTIONS, origin строго https://montazh360.ru, JSON до 16 КиБ. Других публичных методов, чтения заявок или поиска по ID нет.
- repository.py: YDB QuerySessionPool, workload-identity сервисного аккаунта; путь БД допускается только /ru-central1/, TLS endpoint — grpcs://ydb.serverless.yandexcloud.net:2135. Тело заявки находится только в приватной таблице leads.
- schema.sql: leads, lead_requests, lead_limits, lead_outbox; TTL по expires_at. RETENTION_DAYS задаёт владелец, без допустимого значения 1–365 обработчик не принимает заявки. Синтетический тест использует 30 дней; это не утверждённый срок хранения production.
- worker.py: отдельная приватная функция по таймеру раз в минуту. В Telegram уходит только «Новая заявка: расчёт для площадки» и случайный ID. Контакт, площадка, город, активность и комментарий туда не попадают. Приватная ссылка не выдумана: открыть запись можно через YDB Console с IAM-доступом.

Outbox создаётся в той же транзакции, что и заявка. Worker берёт lease на 90 секунд и отмечает успех только после ответа Telegram ok=true с message_id. При ошибке — повтор с задержкой до часа; сама заявка сохраняется независимо от уведомления до согласованного срока хранения. Возможен повтор уведомления с тем же ID, если Telegram принял сообщение, а подтверждение потерялось: это at-least-once, не обещание exactly-once. Повтор не создаёт новую заявку. В логах worker — только агрегированные числа sent/pending_retry; исходные ошибки, URL с токеном и данные клиента не печатаются.

Ограничения приёма: 5 новых заявок с IP за фиксированное 10-минутное окно, 100 новых заявок суммарно за минуту. Сырой IP не сохраняется: bucket использует HMAC с отдельным секретом Lockbox. X-Forwarded-For от клиента игнорируется, источник берётся из requestContext.identity.sourceIp API Gateway. Эти лимиты не заменяют облачные квоты запросов и согласованный денежный лимит.

## Артефакты и локальные команды

```sh
python3 -m unittest tests.test_leads -v
node --test tests/analytics.test.cjs
node --check lead-form.js
python3 backend/deploy/package.py
```

Последняя команда только создаёт output/leads-function.zip: api.py, repository.py, worker.py, requirements.txt. Никаких секретов, тестовой памяти, клиентских данных или файлов с Mac в ZIP нет. gateway.yaml.template — спецификация шлюза; подставляются только два публичных ID ресурсов, не секреты.

## Минимальный путь активации после согласования расходов

1. В существующем облаке Яндекса выбрать папку в ru-central1 и согласовать лимит расходов, срок хранения и ограничение нагрузки. Создать отдельную YDB Serverless для этого сайта с IAM, без анонимных/public прав. Задать ограничение RU/размера и облачные квоты вызовов в пределах согласованного лимита. Применить schema.sql один раз к новой БД.
2. Создать отдельные сервисные аккаунты API и worker с доступом только к этой БД; необходимые роли YDB назначать на эту БД, не на чужие ресурсы. Разместить RATE_LIMIT_PEPPER (случайный секрет минимум 32 символа), TELEGRAM_BOT_TOKEN и подтверждённый личный TELEGRAM_CHAT_ID Александра в Lockbox. Pepper доступен API; токен и chat ID — только worker. Роль lockbox.payloadViewer выдать на нужные секреты; статические ключи сервисных аккаунтов не нужны.
3. Создать две приватные Cloud Functions из одного ZIP, runtime python312: api.handler и worker.handler. Память 256 МБ, timeout API 10 секунд, worker 60 секунд; ограничить параллелизм и число экземпляров согласованной квотой. Обеим передать YDB_ENDPOINT и YDB_DATABASE из карточки БД, сервисный аккаунт и Lockbox-секреты по ссылкам. API также нужны FORM_ENABLED=true, RETENTION_DAYS и CONSENT_VERSION. Worker — NOTIFICATIONS_ENABLED=true. Значения секретов не копировать в публичный Git, команды с токенами или журналы.
4. Создать API Gateway по gateway.yaml.template с отдельным аккаунтом, которому дан functions.functionInvoker только на API-функцию. Не открывать функции через allUsers. Шлюз публичен только для POST/OPTIONS /leads; YDB и worker остаются недоступны анонимному пользователю. Создать приватный минутный таймер для worker с invoker-правами и повторами; настроить наблюдение за pending_retry, ошибками функций и квотами.
5. Подтвердить валидный HTTPS домена. До публичного включения дать URL утверждённых условий обработки данных и их версию. Настройка Вебмастера уже начата владельцем через TXT; дублирующий метатег не нужен.
6. Отправить одну явно синтетическую заявку в облачный API: увидеть её ID и запись в приватной БД, добиться уведомления Александру **только с ID**, проверить повтор и отказ хранилища. Александр — предполагаемый получатель; бот/chat ID пока не предоставлены, настоящая тестовая заявка ему не отправлялась. Проверить, что без IAM нельзя прочитать данные.
7. После успешной проверки задать в публичном lead-config.js enabled=true, HTTPS endpoint шлюза вида https://<id>.apigw.yandexcloud.net/leads, privacyUrl на своём HTTPS-домене и ту же consentVersion. При активации обновить query-версию lead-config.js в HTML, чтобы старый выключенный конфиг не остался в кеше. До этого форма скрыта, телефоны/Telegram работают как раньше. На localhost/github.io форма не активируется даже с production-конфигом.

Итого нужны: согласованный бюджет/квоты и срок хранения, параметры RU-развёртывания, ссылки Lockbox для pepper/бота/chat ID, подтверждённый личный получатель, URL условий и версия согласия, рабочий HTTPS. Аккаунты, счётчик и рекламный кабинет ведёт владелец; новых счётчиков и кампаний код не создаёт.

## Подтверждение заявки и Метрика

Фронтенд валидирует поля, отправляет POST с UUID Idempotency-Key и ожидает JSON ok=true плюс UUID сохранённой заявки. Потеря ответа не очищает заполненную форму; повтор отправляет тот же ключ. В sessionStorage для дедупликации находятся только ключ/хеш payload и случайные ID подтверждённых заявок — не их поля.

lead_form_success вызывается только в подтверждённой ветке; параметры заявки и ID не передаются в цель. contact_click остаётся отдельным справочным событием и не является заявкой. Вебвизор выключен. При недоступной Метрике сохранённая заявка всё равно принимается; клик по телефону, мессенджеру, пустой ответ и ошибка записи не становятся успехом.
